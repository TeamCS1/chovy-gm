By GM8.1 category

Confirmed missing — entire feature areas GM8.1 never had

These have no GM8.1 category to sit under at all — Box2D physics, the buffer/vertex-buffer APIs, shaders, gamepad input, and the platform-integration surfaces (Steam, Facebook, achievements) all arrived after this runner's era.

Deliberately excluded: json_encode/json_decode and the gpu_set_*/gpu_get_* blend/filter controls — neither could be confirmed present in the GMS1.4-era manual specifically (both read as later, 1.99/2.0-era additions), so they're left off rather than guessed. Also excluded: HTML5/Windows 8/Windows Phone-specific functions and advertising/IAP/push-notification/cloud-save APIs, none of which are reachable on a PSP target regardless of runner support.

draw_self() Implemented · confirmed in PPSSPP
  • Registration mechanism — native functions live in a fixed 80-byte (0x50) table at DAT_00123a18, appended by FUN_000045bc(name, funcPtr, argCount, flag). A 4-byte hook at the entry of the draw/display registration routine (one instruction, replaced with a jump to a small trampoline) adds one more call to this table at startup — the only existing code touched anywhere in the runner.
  • The function body — reads the instance's own sprite_index / x / y / image_index / image_xscale / image_yscale / image_angle / image_alpha via 8 getter functions the runner already had, packs them into the same argument shape draw_sprite_ext expects, and tail-calls straight into draw_sprite_ext's own real implementation. No sprite-drawing logic was reimplemented — every call target already existed.
  • Where the new code lives — appended into the runner's own pre-existing free memory (a .bss-style region reserving far more space than it uses), so nothing about the ELF's structure changed. Room here for many more small patches like this one.
  • Tested — a GMS1.4 project's Draw event calling draw_self() now renders the sprite correctly in PPSSPP, with the game running indefinitely instead of the previous silent exit.
clamp() / lerp() / dot_product() Implemented · confirmed in PPSSPP
  • Confirmed genuinely missing — unlike most gaps found via the static scan, these three strings don't exist anywhere in the binary at all, not just unregistered.
  • clamp(value, min, max) needs no new arithmetic: GM8.1 already has real, registered min()/max() functions, so it's implemented as min(max(value, min), max) — copy the arguments into scratch space and delegate, same philosophy as draw_self().
  • lerp(a, b, amt) and dot_product(x1, y1, x2, y2) are genuine new arithmetic, using a newly-confirmed mechanism: unbox each argument to a hardware single-precision float, compute with plain FPU instructions, rebox the result.
  • Two real bugs found and fixed along the way — an early version hooked the registration routine's entry (mirroring draw_self()'s approach exactly) and silently corrupted every other function that routine registers, including string(); the fix hooks its exit instead. A second, separate bug registered all three functions with the wrong argument count (copy-pasted from draw_self(), which correctly takes zero) — both produced the identical silent-exit symptom, isolated by testing with zero calls first, then one function at a time.
  • Tested — a 7-case battery (three clamp(), two lerp(), two dot_product()) passed 7/7 live in PPSSPP.
draw_set_color() / draw_get_color() — Red/Blue swap Fixed · confirmed in PPSSPP
  • Not a missing function — a bugfix to two existing ones. Found while live-testing the full "Drawing: Color & Blending" category: rendering consistently swapped Red and Blue (a pure "red" drew as blue and vice versa), confirmed with three independent visual checks (a red-then-alpha-blue blend, an HSV hue sweep, and a draw_getpixel target rectangle all showed red/blue reversed, green untouched). Matches a real, documented cross-version GameMaker bug (github.com/YoYoGames/GameMaker-Bugs issue #7070).
  • Root cause — make_color_rgb already packs colors in the exact byte order the PSP's GPU wants (confirmed via its own decompile); the function that combines that packed color with the current alpha for the GPU explicitly (and wrongly) swapped the Red and Blue bytes before combining, undoing byte ordering that never needed touching — most likely a porting mistake assuming a PC-style byte layout. draw_get_color()'s own read-back path did the exact mirror-image swap, which had been silently canceling out the render bug for round-trip checks the whole time; fixing only the render side broke it, so both got the same fix.
  • Pure instruction-level patch — the corrected logic needs fewer instructions than the bug it replaces, so both fixes fit inside the original functions' own bounds with no free-memory allocation or hook redirection (tools/runner_patch/patch_color_swap_fix.py, patch_get_color_fix.py).
  • Tested — the full color battery re-run after patching: blend swatch, HSV sweep, and the draw_getpixel target all render with correct colors, and the draw_set_color()/draw_get_color() round-trip checks (never broken until this exact investigation touched them) pass again.
color_get_hue() / color_get_saturation() / color_get_value() Fixed · confirmed in PPSSPP
  • All three were broken, and for the same reason. They share one RGB-to-HSV routine (FUN_000bf1e8), which returned a flat 0 for hue, saturation and value on any input — originally mistaken for a saturation-only fault because pure red's minimum channel happens to be 0 too.
  • Root cause 1 — it computed the minimum twice and the maximum never. The routine holds two consecutive, textually identical three-way comparison blocks. The first correctly finds min(R,G,B); the second is the same code again, but everything downstream treats its result as the maximum (delta = max - min, saturation = delta / max, value = max × 255). With both computing the minimum, delta is always exactly zero, collapsing hue and saturation to 0 and making value report the darkest channel instead of the brightest. Fixed by swapping the operands of that block's three float comparisons, turning each min-select into a max-select.
  • Root cause 2 — saturation was scaled by 2550 instead of 255. The result is written with a byte store, so full saturation wrapped to 2550 & 0xFF = 246 and mid-range values wrapped to nonsense. Hue and value used the correct scales; only saturation carried the stray factor of ten. Fixed by correcting the constant.
  • Five words changed, nothing moved — both fixes are in-place word edits with identical instruction counts, so no free memory or hook redirection was needed (tools/runner_patch/patch_hsv_minmax_fix.py). An earlier conservative workaround that only redirected which value got returned is reverted by the same script.
  • Static analysis was wrong three times here; live debugging settled it. The decompiler attributed the HSV math to the wrong function entirely (raw disassembly showed a 14-instruction byte-repacker), one patch attempt crashed the runner outright, and another regressed a passing test by "fixing" a Red/Blue byte swap that was deliberate and correct all along. What finally identified the bug was a live PPSSPP breakpoint proving a well-formed input still produced 0 — see CLAUDE.md for the full trail.
  • Tested — a 15-colour round-trip battery (make_color_hsv → all three getters, ±4 tolerance for 8-bit quantisation) passed 45/45 live in PPSSPP: all six hue sectors, two mid-sector hues, dark / half-saturated / muted variants, plus the two degenerate cases (a desaturated grey and a zero-value black, both correctly reporting hue and saturation as 0).
Scope limit: this only applies to the opt-in decrypted-EBOOT testing path (PPSSPP only) — there's no way to re-sign a patched EBOOT without Sony's own keys, so a real distributable ISO build is identical for both targets regardless. Standing constraint: the patched runner is used only when the GMS1.4 build target is selected; the GM8.1 pipeline always keeps shipping the original, unpatched runner.

KNOWN RUNNER BEHAVIOR · NOT BUGS IN THIS TOOLCHAIN

Confirmed quirks, found by live-testing on real hardware emulation

All five live in the runner's own compiler/math/string/graphics implementation, untouched by any of the native-code patches above — they apply identically to both GM8.1 and GMS1.4 builds, since both compile against the same underlying runner.

arctan() / arctan2() return radians

GM8.1's own documentation specifies degrees for these two (matching arcsin/arccos, which this runner does return in degrees). Measured live: arctan(1) = 0.785398 (π/4), not 45. Wrap the result in radtodeg() if a GMS1.4 project assumed the documented behavior.

logn() argument order is reversed

Documented as logn(n, x) = log base n of x. Measured live: logn(2, 8) = 0.333 (log₈2), meaning this runner actually computes logn(a, b) = log base b of a. Swap the arguments in any GMS1.4 project's calls.

random_range() breaks on a zero-width range

random_range(5, 5) measured live returned 1072908805 — not close to 5, and shaped like a stray IEEE-754 double misread as an integer, consistent with a divide-by-zero-style bug when min == max. Avoid zero-width ranges with this function on either target.

var must be declared before any other statement in a code action

A var local declared anywhere after other statements in the same code action (the common "declare it right before first use" style) fails on-device with a genuine PSP-side GML compile error — confirmed via a live PPSSPP breakpoint on the runner's compile-error logger, reading back the actual compiler output: unexpected symbol in expression, positioned exactly at the var keyword. The whole action then fails to compile, and the game silently exits with no visible error — the same invisible-logger symptom as every other compile failure in this runner. This was originally misdiagnosed as a bug in string_width() specifically (a deep Ghidra investigation fully cleared that function and its whole font/width-lookup subsystem before live debugging found the real cause). Declare every var local at the very top of a script or code action, before any other statement.

draw_getpixel() always returns 0

Not a logic bug — the actual pixel-read routine (FUN_000cef94) is a literal two-instruction stub (jr ra / nop) that returns immediately without reading anything. Confirmed via raw disassembly: pixel readback from the framebuffer was never implemented on this PSP port at all. A rectangle drawn immediately before calling this function renders correctly on-screen (confirmed visually), proving the drawing itself works fine — only the readback is missing. Implementing this for real would mean writing genuinely new code (querying the PSP's actual framebuffer address and indexing into VRAM in the correct pixel format), not patching existing logic — a different category of work than every other fix on this page. Don't rely on draw_getpixel() on this runner.
