# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

chovy-gm ("Chovy-GayMaker") is a decompiled and patched build of YoYoGames' internal GameMaker Asset Compiler v1.0.98, modified to exclusively target the Sony PSP. It takes a standalone GameMaker 8/8.1 executable (a self-contained `.exe` a game was exported to) and recompiles its assets/GML scripts into a PSP-native package, then assembles a bootable PSP/PSVita ISO around it using an unreleased YoYoGames PSP "runner" (from the PSP minis `Karoshi` or `GreenTechPlus`).

This is C#/.NET Framework Windows Forms desktop software, not a web or cross-platform project. It is inherently Windows-only (registry access, WinForms, x86 P/Invoke-adjacent unsafe code).

## Build

Requires Visual Studio 2013 (or a compatible MSBuild with the v12.0 toolset) and the .NET Framework 4.6.1 targeting pack, on Windows.

NuGet packages are already vendored under `packages/` (old-style `packages.config`, not `PackageReference`), so a fresh clone does not need `nuget restore` to build.

Build with MSBuild (VS2013's `MSBuild.exe`, or a modern one — VS2022's works fine despite the `ToolsVersion="12.0"`/`VisualStudioVersion = 12.0` markers in the project files):

```
MSBuild.exe GMAssetCompiler.sln /p:Configuration=Release /p:Platform=x86
```

- Only `Debug|x86` and `Release|x86` configurations exist — there is no AnyCPU or x64 build.
- Output assembly name is `CHOVY-GM.exe` (see `AssemblyName` in `GMAssetCompiler.csproj`), despite the root namespace being `ChovyUI`. Build output lands in `bin\Release\` (or `bin\Debug\`) alongside `Ionic.Zip.Reduced.dll`/`NAudio.dll`.
- There is no test project, no CI configuration, and no lint/formatter config in this repo.
- **`TargetFrameworkVersion` is `v4.7.2`**, not the `v4.6.1` the project originally shipped with. It was bumped because a VS2022 install can have the 4.6.1 targeting pack registered but hollow (IntelliSense XML docs present, actual reference DLLs missing — `Get-ChildItem ...\.NETFramework\v4.6.1 -Filter *.dll` returns nothing), which fails the build with `MSB3644`. 4.7.2/4.8 are drop-in compatible for this codebase and typically have the DLLs present; if `MSB3644` reappears on a different machine, check `.NETFramework\v4.7.2` similarly before assuming a full dev-pack install is required.

## Running

The built `.exe` expects to sit alongside a specific runtime folder layout (shipped in the GitHub release zips, not committed to the repo):

- `RUNNER\` — the PSP ISO skeleton (`PSP_GAME\SYSDIR\{KAROSHI,GREENTECHPLUS}.BIN`, `PARAM.SFO`, etc.) that gets copied and patched per build.
- `IMG\ICON0.PNG`, `IMG\PIC0.PNG` — default PSP icon/pic assets.
- External tools referenced by the README but not part of this source tree: Sony's `umdgenc` (official UMD ISO builder), `at3tool` (WAV → Sony `.at3`), and `fluidsynth` (MIDI → WAV for in-game music).

Launching the exe with no arguments shows the `ChovyUI` dialog first (pick a GM 8/8.1 exe, PSP Title ID, icon/pic, and controller button mapping — persisted to `HKCU\Software\CHOVYProject\Chovy-GM`), plus a separate black "CHOVY-GM Build Log" console window that opens alongside it — a WinForms app has no console attached by default, so this is the only place build warnings and progress messages (compile-time GML validation warnings, DND-action skip notices, etc.) are visible when running the GUI rather than `--headless`. Clicking "BUILD ISO" stages `RUNNER\` into `<gmexe dir>\_iso_temp\`, then `Program.Main` re-invokes the compiler in `-c` (compile-only) mode against the chosen exe. The dialog also requires `RUNNER\` and a valid 144×80 `icon0.png`/`pic0.png` to exist at `Application.StartupPath` (i.e. next to the exe) before "Build ISO" enables at all — these ship in the GitHub release zips, not the source tree, so a fresh dev checkout needs them placed manually (`bin\Release\RUNNER\`, `bin\Release\IMG\ICON0.PNG` + `PIC0.PNG`) the same as the native DLLs below. After the build finishes, the console waits for a keypress before closing — without it, the process (and its console window, since `CompileOnly` mode never calls `Application.Run`) would exit and vanish the instant the build finished, taking the very output you'd want to read with it; `--headless` deliberately skips this pause; it must stay non-interactive for scripted/CI use. CLI options are also parseable directly via `NDesk.Options` (`-?` for the list), but `SetMachineType` currently hardcodes PSP regardless of the `-m` flag passed.

**A missing `umdgenc.exe` used to crash the whole app instead of just skipping the ISO step.** `UMDGEN.CreateISO`'s `Process.Start()` threw an unhandled `Win32Exception` with no `try`/`catch` anywhere above it, killing the process (Windows logs this as a ".NET Runtime" Application-log error, `System.ComponentModel.Win32Exception` at `Process.StartWithCreateProcess`) — and since a WinForms app's console window closes the instant its process dies, this made the build log genuinely unreadable in the GUI: you'd see it fill with progress right up until the crash, then the whole window would disappear before you could read anything, including the exception itself. Fixed in two places: `CreateISO` now returns `bool` and catches the failed `Process.Start()`, and `IFFSaver.Save` checks that result before running its post-build steps (deleting `umdgenc`'s intermediate files, moving `USER_L0.IMG` to the final `.ISO` path) — all of which previously ran unconditionally and threw their own follow-on `FileNotFoundException` once `CreateISO` silently did nothing. `game.psp` (the actual GameMaker-side compile output) was always written successfully before this point regardless — only the final Sony-tool ISO-packing step was ever affected. Deliberately no `MessageBox` on this path: it fires on *every* `--headless` run too (this external tool is essentially never present in a dev/CI setup), and a modal dialog there would hang forever with nobody to click it.

**Without `umdgenc.exe`, there is still no single file to hand to an emulator — and even with it, the result wouldn't boot in PPSSPP anyway.** A GUI build (or `--headless`) leaves you with the staged `<output>\_iso_temp\` folder (containing `game.psp` and an `EBOOT.BIN`), not a `.ISO`, unless `umdgenc.exe` is present to pack it. But *even a successfully-packed ISO* wouldn't help with PPSSPP testing: `EBOOT.BIN` at that point is just the original Sony-encrypted `KAROSHI.BIN`/`GREENTECHPLUS.BIN` renamed, and PPSSPP flatly refuses encrypted EBOOTs (see the reverse-engineering notes above). Every PPSSPP test all through this file, before the option below existed, was done by decrypting the runner once (`pspdecrypt`) and manually overwriting `_iso_temp\PSP_GAME\SYSDIR\EBOOT.BIN` with that decrypted copy before pointing PPSSPP at the `_iso_temp` folder.

**That manual swap is now automatable, opt-in, in both the GUI and `--headless`.** `ChovyUI.StageDecryptedEbootForTesting` (called from a new "Stage decrypted EBOOT for PPSSPP testing" checkbox in the GUI, unchecked/off by default and persisted to the registry same as other settings, or from `--headless`'s `--decrypt-eboot` flag — can appear anywhere after the required positional args) overwrites the just-staged `EBOOT.BIN` with a pre-decrypted copy, right after the normal Karoshi/GreenTech+ selection logic and before the actual GML compile runs, so it survives all the way through to the final `_iso_temp` folder (and into a packed `.ISO` too, if `umdgenc.exe` is present — `IFFSaver`/`UMDGEN` just package whatever's already sitting in that folder). A real distribution build simply leaves the checkbox/flag off and is completely unaffected — this never touches the actual `RUNNER\` template's own encrypted files, only the per-build staged copy.
- **Where the decrypted files live**: `RUNNER_DECRYPTED\KAROSHI.BIN` / `GREENTECHPLUS.BIN`, next to the exe (`Application.StartupPath`) — mirroring the `RUNNER\` template folder's own convention exactly. Like `RUNNER\` itself, these are **not shipped or committed to the repo** (derived from Sony-signed content, and `bin\` is gitignored regardless) — decrypt the two runner binaries yourself once (see the Ghidra/`pspdecrypt` reverse-engineering notes above) and place them there. If the files aren't present, staging is skipped with a clear console warning rather than failing the build — safe to enable unconditionally, including in `--headless`/CI, even on a machine that's never done this decryption step.

**Headless mode** (added on top of the original tool, for scripted/CI-less testing without the WinForms dialog):

```
CHOVY-GM.exe --headless <gm81.exe> <output dir> <RUNNER template dir> [titleID]
```

This replicates exactly what `ChovyUI.BuildISO_Click` + compile-only mode do (stage `RUNNER\` into `<output dir>\_iso_temp\`, select the `KAROSHI.BIN` runner as `EBOOT.BIN`, compile), without needing icon/pic files or a GUI session. Default `titleID` is `TEST00000` if omitted. See `Program.Main`'s `--headless` branch.

**Native DLLs required at runtime, not restored by NuGet or committed to this repo** — copy them into `bin\Release\` (or wherever the exe runs from) from a release zip / real PSP toolchain before compiling anything for real:
- `squish.dll` — the DXT texture compressor `Squish.cs` P/Invokes into. Without it, compilation dies with `DllNotFoundException` right at the texture-writing stage.
- `PVRTexLib.dll` — `squish.dll`'s own dependency (texture format conversion backend).
- `msvcr90.dll` (VC++ 2008 CRT) — also a `squish.dll` dependency. It's commonly present system-wide only as a WinSxS side-by-side assembly (`C:\Windows\WinSxS\x86_microsoft.vc90.crt_*`), and `squish.dll` apparently lacks the manifest needed to bind to it there — a private/loose copy next to the exe is the reliable fix (`Microsoft.VCRedist.2008.x86` via winget installs the WinSxS assembly to copy from).

Without these three, compilation gets all the way through asset/audio parsing and dies specifically at DXT texture compression.

If the source game has MIDI music, two more externals are needed to convert it (`fluidsynth.exe`, `gm.sf2`, plus `fluidsynth`'s own DLLs: `libfluidsynth-2.dll`, `libglib-2.0-0.dll`, `libgobject-2.0-0.dll`, `libgthread-2.0-0.dll`, `libinstpatch-0.dll`, `libsndfile-1.dll`) — all present in the release zips, same story as the texture DLLs above. Without them, compilation fails specifically at the `Converting ... To .WAV` step for any `.mid` audio resource; games with only `.wav` sounds don't need this.

## Architecture

### Compile pipeline (in order)

1. **`Loader`** (`GMAssetCompiler/Loader.cs`) — reads the target file. If it's a GM8.1 exe, it locates and XOR/CRC-decrypts (`CheckFor8_1`/`Process_Encrypt`) the embedded GMK-format asset blob, then parses it into a `GMAssets` graph. It can also re-read an already-compiled `.psp` IFF file chunk-by-chunk for debugging (`LoadPSP`) — several chunk types (`FONT`, `TMLN`) are deliberately skipped there because parsing them crashes on real PSP game files.
2. **GML compilation** — `GMLCompile`/`Lex`/`LexTree`/`GMLToken` tokenize and parse GameMaker Language source pulled from `GMAssets`; `GML2VM` compiles it to the bytecode VM format (`eVM_Instruction`, `VMBuffer`) that the PSP runner interprets. `GML2JavaScript` and `YYObfuscate` are dead code paths inherited from the original HTML5 export target.
3. **Texture packing** — `TexturePage`/`TexturePageEntry`/`Texture`/`Squish` (a DXT compressor port) pack sprite/background bitmaps into fixed-size pages per `IMachineType.TPageWidth/Height` (512×512 for PSP), encoded as DXT (`DDS.cs`).
4. **`IFFSaver`** (`GMAssetCompiler/IFFSaver.cs`) — the actual output writer. Always writes to `<OutputDir>\_iso_temp\PSP_GAME\USRDIR\games\game.psp` regardless of the name passed in — this hardcoded path is what ties compilation to the ISO staging area `ChovyUI` already created.
5. **`UmdGen.UMDGEN`** (`UMDGEN.CS`) — generates the `.ufl`/`.umi` sector-layout manifest files Sony's `umdgenc` needs to actually burn `_iso_temp\` into a bootable ISO. This step is not invoked automatically by this codebase; it's documented as an external post-processing tool.

### The machine-type abstraction is now vestigial

`IMachineType` (`GMAssetCompiler/IMachineType.cs`) and `GMAssetCompiler.Machines\{PSP,Android,IOS,Symbian,Windows,HTML5}.cs` are inherited from when this compiler targeted many GameMaker export platforms. Only `PSP.cs` is exercised — `Program.SetMachineType` force-overwrites any requested machine to `"psp"`. The other four machine classes and their associated savers (`HTML5Saver`, obfuscation, texture-group JS handling in `Program.cs`) are unreachable/untested leftovers; treat them as reference material, not working code paths.

### `GMAC1098/`

A near-complete duplicate copy of the project tree, representing the pre-patch decompiled baseline (GameMaker Asset Compiler v1.0.98 before PSP-specific modifications). It's kept for diffing against the current patched sources (see `GMAC1098/how it should be!.log` / `how it shouldnt be.log`) and is not part of the build — the root `GMAssetCompiler.sln`/`.csproj` only reference the top-level sources.

### `ChovyUI` vs `GMAssetCompiler.Form1`

Two separate WinForms UIs exist: `ChovyUI` (root namespace, `ChovyUI.cs`) is the PSP-packaging front-end shown at startup (title/icon/controller config, "BUILD ISO" button). `GMAssetCompiler.Form1` is the original GameMaker Asset Compiler's own asset-browser/compile UI, still invoked when `Program.Main` runs without `-c`/`CompileOnly`.

### Logging

`GMAssetCompiler.Trace` writes to `TraceGMA.log` next to the executable, gzip-rotating it past 200KB and pruning `.gz` archives older than 30 days.

## The PSP runner (`KAROSHI.BIN`/`GREENTECHPLUS.BIN`) — reverse-engineering notes

These are not homebrew ELFs; they're Sony's standard signed/encrypted module format (`~PSP` header — module name embedded at offset `0x0C` literally reads `"Runner"`). This is a separate, PSP-hardware-level encryption layer (KIRK engine, tag-keyed) from the PSN PKG/RIF licensing used only for the original store *distribution* of the Minis — since these files are already-extracted, post-install EBOOTs, only the module encryption applies.

**Decrypting them** doesn't require real hardware: [`John-K/pspdecrypt`](https://github.com/John-K/pspdecrypt) (GPLv3, decryption code lifted from PPSSPP itself, MIT/public-domain `libkirk` crypto with the historically-recovered PSP root keys) decrypts both files offline. Its `pspDecryptPRX()` in `PrxDecrypter.cpp` + `libkirk/*.c` is fully self-contained (no OpenSSL/zlib needed — those are only pulled in by the unrelated PSAR/firmware-updater code paths in that repo). Both `KAROSHI.BIN` and `GREENTECHPLUS.BIN` decrypt cleanly under the same signing tag (`D9160BF0`), confirming it's a publicly-known key, not something exotic. Output is a plain 32-bit MIPS ELF.

**Testing the decrypted runner in PPSSPP:**
- PPSSPP flatly rejects the *encrypted* file regardless of naming/extension tricks (`Identify_File` in `Core/Loaders.cpp` never gets a chance to accept it) — decrypt first.
- Boot the **`_iso_temp` folder itself**, not the loose `EBOOT.BIN` file directly. Pointing PPSSPP at the bare EBOOT file skips the `disc0:` virtual filesystem mount, so the runner's own `sceIoOpen("disc0:/PSP_GAME/USRDIR/games/game.psp", ...)` calls fail with `NODEV` and it never sees your compiled data at all, even though the file is sitting right there. Booting the folder (which PPSSPP recognizes as `PSP_DISC_DIRECTORY` since it contains a `PSP_GAME` subfolder) mounts `disc0:` properly.
- Use `CPUCore = 0` (Interpreter) in `ppsspp.ini`, not the default JIT. Under JIT the runner segfaults PPSSPP itself (host-level `0xc0000005`, confirmed via Windows Event Log) partway through generic PSP SDK init code — this reproduces with *just the bare runner*, no GameMaker content involved, so it's a PPSSPP JIT-recompiler bug tickled by this old/unusual code, not a bug in the runner or in compiled output. The interpreter runs the identical code without crashing (just much slower).

### The pipeline works end-to-end — confirmed

**A real GM8.1 game, compiled by this tool, boots and plays as an actual running game** through the decrypted Karoshi runner in PPSSPP. This was confirmed with a second, smaller test game (`neonquest.exe`, ~6.8MB) after an initial test game (`Pillar of Autumn V1.exe`, ~37MB) reproducibly got stuck at the splash screen and exited instead of starting. That first result briefly looked like it might be a fundamental problem with the runner or pipeline (see reverse-engineering notes below); the second game proved otherwise. **Treat any single-game failure as game-specific until proven otherwise — always cross-check against a second, different compiled game before suspecting the compiler or runner.**

### Reverse-engineering toolchain for the runner (Ghidra, headless)

Standalone Ghidra doesn't understand the PSP's ELF flavor (custom relocation types, NID-keyed import table) out of the box. The working setup:
- [`kotcrab/ghidra-allegrex`](https://github.com/kotcrab/ghidra-allegrex) — Ghidra processor/loader extension adding the Allegrex CPU and PSP ELF support. Install by extracting its release zip into `<ghidra install>/Ghidra/Extensions/`. Import with language `Allegrex:LE:32:default`; Ghidra then auto-detects the loader as "PSP Executable (ELF)".
- [`pspdev/psp-ghidra-scripts`](https://github.com/pspdev/psp-ghidra-scripts)' `SonyPSPResolveNIDs.py` resolves the NID-keyed import table to real function names (`sceKernelExitGame` etc.) using its bundled `ppsspp_niddb*.xml`. **It's a Jython script and Ghidra 12.x dropped Jython for PyGhidra** — running it needs either a working PyGhidra install (its `pyghidra_launcher.py` will try to `pip install` a JPype wheel that has no prebuilt binary for a very new Python, then falls back to compiling it, which needs MSVC build tools — a heavy, avoidable detour) or a **from-scratch Java port** of the same logic, which is what actually got used here: a `GhidraScript` subclass parsing `PspModuleImport`/`PspModuleInfo` via `CParser`, reading the same NID XML with `javax.xml.parsers`, calling the same `createFunction`/`createLabel` flat-API methods. Entirely scriptable via `support/analyzeHeadless <project dir> <name> -import <elf> -processor Allegrex:LE:32:default -scriptPath <dir> -postScript <Script>.java` — no GUI needed for any of this.
- **Correlating a Ghidra (static) address to a live PPSSPP address**: they differ by a constant offset, but it is *not* safely guessable (image base 0x08800000 is common lore but not exact here) and PPSSPP's own thread-entry-point column in its Threads panel is *also* not the right reference (it's a specific thread's start function, not the module's). The one reliable way: find one instruction Ghidra resolved to a named import call (e.g. a `jal sceKernelExitGame`), find the *same* call live in PPSSPP's disassembly (matching the surrounding instructions, not just the address), and subtract. Cross-check against a second independent instruction match before trusting the offset — two wrong guesses preceded the correct one in this session. A correct offset should also satisfy: `live_root_thread_entry - offset == e_entry` read straight from the raw ELF header (`Elf32_Ehdr.e_entry` at file offset `0x18`).
- PPSSPP's own "Save .sym file" (Debug menu) reliably crashes it when used against this runner, timing-independent — don't rely on it; the Java NID-resolution route above is the practical path to readable names.

### RESOLVED (proof of concept) — `draw_self()` patched into the runner as real native code, confirmed rendering in PPSSPP

Goal: implement `draw_self()` (and, in principle, any other GML function this runner's GML compiler table is missing entirely, per "The runner's full GML support surface" above — `d3d_light_define_ambient`, `point_distance_3d`, `clamp`, `lerp`, etc.) as real native code patched into the runner binary, rather than just working around its absence at the loader/compiler level. **This must only ever apply when the GMS1.4 target is selected** — the GM8.1 pipeline must keep using the original, unpatched runner unconditionally.

**Done, as a proof of concept**: `draw_self()` is now a real, working native function in a patched copy of the runner, confirmed end-to-end in PPSSPP — `obj_player`'s Draw event (`Sample.gmx`) calling `draw_self()` renders the player sprite on screen, alongside the font text and room tiles, with the game running indefinitely (no exit). This is not yet wired into the actual build pipeline (`ChovyUI`/`Program.cs` still only know about the stock runner) — it exists as an offline patcher tool plus a manually-substituted test file. Wiring it in for real (see "Next step" below) is the only remaining piece.

**The function registration mechanism is fully understood and is trivially extensible:**
- At module init, one function (`FUN_00046424` for display/draw functions; parallel sibling functions elsewhere for other categories like `instance_*`) calls `FUN_000045bc(name, funcPtr, argCount, flag)` once per built-in — e.g. `FUN_000045bc("draw_sprite", FUN_00041748, 4, 0)`.
- `FUN_000045bc` appends a new fixed-size (`0x50`/80-byte) entry to a single growable array at `DAT_00123a18` (reallocated 500 entries at a time via `FUN_000eeda4` when full — plenty of headroom, and it grows itself automatically). Each entry: name string inline at offset `0x00` (up to 0x40 bytes), function pointer at `0x40`, registered arg count at `0x44`, a 1-byte flag at `0x48` (`0` for plain functions like `draw_sprite`/`instance_destroy`, `1` for at least the `_ext`-style/extended variants like `draw_sprite_ext` — meaning likely "has optional/variadic trailing args", not yet confirmed further), a `0xffffffff` sentinel at `0x4c`.
- **Adding a new function is just one more call to this same `FUN_000045bc`** (e.g. `FUN_000045bc("draw_self", <new_func_addr>, 0, 0)`) inserted anywhere that runs before the GML compiler starts resolving identifiers — no static table restructuring needed, since it's a runtime append.
- Name→index resolution happens once, at **compile time** (inside the same `FUN_00005284` pipeline documented elsewhere in this file) — compiled bytecode never carries the name again, only a resolved integer index (confirmed both from the runner's own `FUN_0000470c(index)`, which fetches an entry's arg-count by raw index with a `< 100000` built-in / `>= 500000` script range split, and from this repo's own `GML2VM.cs`: `EmitI(eVM_Instruction.eVMI_CALL, _tok.Id)` — the VM's `CALL` opcode's only operand is that resolved index).

**The VM bytecode interpreter and its native-call ABI are fully understood:**
- `FUN_00013bc4` is the bytecode interpreter loop — confirmed beyond doubt by an embedded source filename string it references, `"Files/Code/VM_Exec.cpp"`. It fetches one instruction word at a time, extracts the opcode as the top byte (`instrWord >> 0x18`), and dispatches through nested range-checked `if`/`switch` blocks matching `eVM_Instruction`'s actual values (confirmed: `eVMI_CALL = 218 = 0xDA` in `eVM_Instruction.cs`, and the interpreter's `0xda`/`0xdb` boundary check routes opcode `0xDA` specifically to `FUN_000138c8`).
- `FUN_000138c8` is the actual "invoke a registered function by index" handler (and was independently already found reading `DAT_00123a18` directly, before this opcode-tracing confirmed it). For a built-in (index `< 100000`): it zeroes a 16-byte return-value slot, then does `(**(code**)(DAT_00123a18 + index*0x50 + 0x40))(&returnSlot, ctxA_or_self, ctxB, argCount, argsArrayPtr)`, then frees any string-typed consumed arguments and copies the 16-byte return value back onto the VM operand stack in their place.
- **This gives the definitive native-function ABI**: `void FuncImpl(Variable* returnSlot, void* self, void* ctxB, int argCount, Variable* args)` — a fixed 5-parameter signature for *every* native function regardless of its own declared GML arg count (Ghidra's decompiler often hides the parameters a given function doesn't happen to touch, which is why e.g. `draw_sprite`'s decompiled signature only shows 5 total params that read like "4 real args + 1 context" rather than this literal 5-slot shape — don't trust an individual function's apparent parameter count as the ABI; trust the caller, `FUN_000138c8`, instead).
- **The 2nd parameter is confirmed to be the current/self instance pointer**: `instance_destroy` (registered as `FUN_000301dc`, 0 GML args, flag `0`) decompiles as `FUN_000301dc(param_1, param_2) { FUN_00099ed0(param_2); }`, and `FUN_00099ed0(param_1) { ...; *(byte*)(param_1+4) = 1; }` — setting what's unmistakably an "is destroyed" flag at `self+4`. Since `instance_destroy` needs no GML arguments at all, the only plausible source for "which instance" is this implicit ABI slot.
- **`Variable` (the boxed GML value passed on the VM operand stack / in `args`) is a 16-byte struct**, confirmed via `draw_sprite_ext`'s own body: it reads 8 arguments' worth of doubles as consecutive pairs at `args+0x28/+0x2c`, `+0x38/+0x3c`, `+0x48/+0x4c`, ... each pair exactly `0x10` apart — i.e. argN's double value lives at `args + N*0x10 + 8`, meaning each 16-byte `Variable` is shaped roughly `{ int32 typeTag; int32 unused_or_stringptr; double value; }` (the first two 4-byte words are skipped by the numeric-argument path; a type-tag value of `1` specifically means "string", per the post-call cleanup loop in `FUN_000138c8` that frees `args[i]`'s pointer when `args[i].typeTag == 1`).

**All 8 instance-struct field offsets `draw_self()` needs are now confirmed**, found the same way as `instance_destroy`'s `self+4` flag: every built-in instance variable is registered in one place, `FUN_000ae484`, as a call `FUN_000a5690(name, getterFn, setterFn, flag)` per variable (this is the *variable* equivalent of the `FUN_000045bc` *function* registration table — same "one append call per built-in" shape, different table). Decompiling the 8 relevant getters (each just `outVar.tag = 0; outVar.value = convert(*(self + OFFSET));`, matching the confirmed 16-byte `Variable` layout) gives:

| Field | Offset | Getter | Setter |
|---|---|---|---|
| `x` | `self+0x3c` | `FUN_000acc8c` | `FUN_000ad940` |
| `y` | `self+0x40` | `FUN_000accc4` | `FUN_000ad980` |
| `sprite_index` | `self+0x14` | `FUN_000ad27c` | `FUN_000adf18` |
| `image_index` | `self+0x18` | `FUN_000ad2b4` | `FUN_000adf74` |
| `image_xscale` | `self+0x20` | `FUN_000ad588` | `FUN_000ae02c` |
| `image_yscale` | `self+0x24` | `FUN_000ad5c0` | `FUN_000ae068` |
| `image_angle` | `self+0x28` | `FUN_000ad5f8` | `FUN_000ae0a4` |
| `image_alpha` | `self+0x2c` | `FUN_000ad630` | `FUN_000ae108` |

(`x`/`y`'s names are stored as data-label string pointers rather than inline literals in Ghidra's decompilation — `&DAT_0011b0e0`/`&DAT_0011b0e4` — everything else prints as a normal C string; both resolve to `"x"`/`"y"` in the binary's `.rodata`.)

**This changes the plan for `draw_self()`'s body for the better**: rather than re-deriving each field's raw-to-double conversion (`FUN_000fcbc4` for most, `FUN_000fd6b4` for `sprite_index` specifically — never fully characterized, and now unnecessary to), the new function can just **call these 8 existing getters directly** (same tiny calling convention as everything else here: `getter(self, 0, &outSlot)`), write their results straight into a 9-slot `Variable` array shaped exactly like `draw_sprite_ext`'s own argument list — `[sprite_index, image_index, x, y, image_xscale, image_yscale, image_angle, color, image_alpha]`, with `color` hardcoded to white/no-blend (`16777215.0`) since it isn't one of the 8 tracked fields — and tail-call `FUN_000417e4` (`draw_sprite_ext`'s real implementation, already fully decompiled above) with that array and the same `self`/`ctxB`. Confirmed from `FUN_000417e4`'s own body: it reads `args[2..8]` (`x` through `alpha`) at 16-byte strides starting `args+0x28`, with `args[0]`/`args[1]` (sprite/subimage) consumed earlier by its `FUN_00041650` sprite-resolve helper — a 9-argument call, matching GM8's real `draw_sprite_ext(sprite, subimg, x, y, xscale, yscale, angle, color, alpha)` signature exactly. Net result: `draw_self()`'s entire body is ~9 calls to functions that already exist plus one final call — no reimplemented sprite/draw logic, exactly the "zero new logic" framing this started from.

**How the patch is actually built and injected** — a from-scratch tool in `tools/runner_patch/` (outside the shipped C# project; it produces a patched runner *file*, and only that output file needs to reach the build tool, per the "maintainability" concern that prompted this design):
- `mips_asm.py`: a deliberately tiny MIPS32/o32 encoder (`lui`/`ori`/`addiu`/`lw`/`sw`/`or`/`jal`/`j`/`jr`/`nop` — exactly what's needed, not a general assembler). Every encoding was cross-checked byte-for-byte against real compiler-emitted instructions already sitting in the runner (e.g. `addiu sp,sp,-0x10`, `sw ra,0x0(sp)`, `lui a0,0x12`, the `or $rd,$zero,$zero` idiom Ghidra prints as `li $rd,0`) before being trusted for new code — all matched exactly.
- `patch_draw_self.py`: builds two new routines and appends them into the runner's own free space, then does exactly one 4-byte edit to existing code:
  1. **`draw_self_impl`** — the actual native function. Calls the 8 confirmed getters directly (`getter(self, 0, &args[i])`), builds a 9-slot `Variable` array shaped like `draw_sprite_ext`'s real argument list (`sprite, subimg, x, y, xscale, yscale, angle, color, alpha`, with `color` hardcoded to white/`16777215.0` since it isn't one of the 8 tracked fields), and tail-calls `FUN_000417e4` (`draw_sprite_ext`'s real implementation) with it. ~270 bytes, zero re-derived business logic.
  2. **A hook trampoline** — patched into `FUN_00046424`'s entry (the draw/display function-registration routine) as a single `j trampoline` overwriting its first instruction (`addiu sp,sp,-0x10`). The trampoline re-executes that displaced instruction for real, calls `FUN_000045bc("draw_self", draw_self_impl, 0, 0)` to register the new function, restores the register `FUN_00046424`'s own next instruction had already half-built, and jumps back into `FUN_00046424` to resume normally. This is the *only* existing code touched, and only 4 bytes of it.
  3. **Where the new bytes actually live**: the runner's ELF program header [1] is a `.bss`-style `PT_LOAD` segment — only `0x248` bytes of real file data (`p_filesz`), but `0x2ba6b9` bytes (~2.8MB) reserved as zero-fill memory (`p_memsz`). The new code (plus a `"draw_self\0"` name string, ~350 bytes total) is appended right after the existing real data and `p_filesz` is extended to cover it — nothing about the ELF's structure changes, and there's room here for hundreds of future small functions this same way, not just this one. (Ghidra's own ELF loader still shows this region as "uninitialized" past the *original* boundary, because it keys that off the ELF's *section* headers, which weren't touched — a display quirk of the analysis tool, not of the actual runtime loader, which uses *program* headers exclusively; PPSSPP loading and running the patched code end-to-end is the real proof this distinction doesn't matter at runtime.)
- All jump/call targets are verified to share the same top address nibble as their call site before assembly (a hard requirement for MIPS `j`/`jal`, which only replace the low 28 bits of PC) — trivially true here since everything lives in the same sub-3MB module image, but checked in code rather than assumed, so it stays correct if future functions get placed much further away.

**A real gotcha hit during testing, worth remembering**: PPSSPP's two "run this" paths are not equivalent. Pointing PPSSPP directly at `EBOOT.BIN` (as a file, or via the CLI arg) booted the patched build, ran briefly, and silently exited back to the game browser — the exact "no visible error" symptom this whole investigation started from, and initially looked like the patch had failed. It hadn't: loading the **same build as a directory** (File → Open Directory, pointed at the `_iso_temp` folder containing `PSP_GAME\...`) — the full unpacked-UMD path, closer to what a real ISO boot does — ran it correctly, rendering the sprite via `draw_self()` with the game staying up indefinitely. Direct-EBOOT loading is evidently missing something a full UMD-folder/ISO boot provides (most likely correct `PARAM.SFO`/`umd:` filesystem context that `game.psp`'s own file-loading code expects) — this failure mode is about *how the test was launched*, unrelated to the patch itself, but is exactly the kind of thing that looks identical to a real silent crash. When testing any future patched runner, load it as a directory (or a real built ISO once `umdgenc.exe` is available), never a bare `EBOOT.BIN`.

**Wired into the build pipeline (done).** `StageDecryptedEbootForTesting` (`ChovyUI.cs`) now takes the current `eGMTarget` and picks the source file itself: GMS1.4 → `RUNNER_DECRYPTED\KAROSHI_GMS14PATCHED.BIN`, GM8.1 → the standard `KAROSHI.BIN`, unconditionally — the two are genuinely separate files now, never a shared one mutated based on which target ran last. Both call sites (`ChovyUI.BuildISO_Click`'s GUI checkbox and `Program.cs`'s `--headless --decrypt-eboot` path) pass the real selected target through (`GetTarget()` / the already-parsed `Target` variable respectively). Verified via `--headless`: a `gms14` build stages `KAROSHI_GMS14PATCHED.BIN`; a `gm81` build (tested against `neonquest.exe`) stages the untouched `KAROSHI.BIN` — confirmed by the "Staged decrypted EBOOT.BIN... (from ...)" log line naming the right file in each case. GreenTechPlus has no patched variant yet, so GMS1.4+GreenTechPlus falls back to the standard `GREENTECHPLUS.BIN` with an explicit warning rather than silently claiming to be patched.

**Scope limit worth remembering**: this only ever affects the opt-in decrypted-EBOOT *testing* path (PPSSPP-only, never a real signed EBOOT) — there's no way to re-encrypt/re-sign a patched EBOOT without Sony's actual keys, so a real distributable ISO build (the `RUNNER\` encrypted template, `StageDecryptedEboot` unchecked) is identical for both targets regardless of any runner patch. "GMS1.4 gets the patched runner" currently means "GMS1.4's PPSSPP test builds do" — not real hardware builds.

`GMLFunctionValidator` was also made target-aware to match: `ValidateAssets`/`FindUnsupportedCalls` take an `_isGms14Target` flag (`Loader.LoadGMS14Project` passes `true`, `Loader.LoadGMK`'s GM8.1 path defaults to `false`), checked against a small `Gms14PatchedAdditions` set (currently just `draw_self`) so a GMS1.4 project calling it no longer gets a misleading "unsupported" warning, while a GM8.1 project calling it still correctly does (that target never gets the patch).

**Reusable scripts added to `ghidra_scripts/` for this investigation** (all safe to rerun/adapt): `FindStringXrefs.java` (given a string literal, finds and decompiles every function referencing it — used to find both the `FUN_00046424`-style function-registration call sites and, retargeted, `FUN_000ae484`'s instance-*variable* registration table), `FindTableReaders.java` (finds every function referencing a given data address, e.g. the `DAT_00123a18` table base, beyond just its known writers), `FindOpcodeDispatch.java` (scans every instruction in the binary for an immediate operand matching given numeric values — used to find the `0xda`/`0xdb` opcode-bound checks that led to the VM loop), `FindCodeCave.java` (scans executable memory blocks for long zero-byte runs — came back empty here, correctly, since the real free space turned out to be the non-executable `.bss` segment instead), `DumpAllBlocks.java` (lists every Ghidra memory block with its permissions/init state — how the `.bss` gap was actually found), `DumpDisasmAt.java` (raw disassembly, not decompiled C, at a given address — needed to see the exact instructions a hook would displace), `VerifyPatch.java` (re-disassembles/decompiles a freshly-patched ELF's injected addresses as a sanity check before real hardware/emulator testing). `FindCallSites.java`'s broad "any indirect call near an 0x40 offset" attempt drowned in noise from the ubiquitous, unrelated `lw ra,0x40(sp)` stack-frame-restore pattern and was deleted rather than reused.
### RESOLVED (very high confidence) — `Pillar of Autumn`'s splash-then-exit

With the pipeline confirmed working via `neonquest.exe`, the `Pillar of Autumn V1.exe` splash-then-exit was narrowed to a single-game compatibility question rather than a pipeline bug. What was ruled out for it via static analysis of `karoshi_decrypted.elf` (all function addresses below are Ghidra/static, not live):
- Not a PSN/DRM check — `FUN_000ce54c` (the post-load "gate" `main()` checks) has no conditional logic at all, just ~13 fixed subsystem-init calls and an unconditional `return 1`.
- Not a chunk-parsing rejection — `FUN_000c5790`'s chunk dispatch recognizes every chunk tag this compiler writes (`GEN8`, `OPTN`, `SPRT`, `SOND`, `BGND`, `PATH`, `SCPT`, `FONT`, `TMLN`, `OBJT`, `ROOM`, `DAFL`, `TPAG`, `STRG`, `TXTR`, `AUDO`); the `FORM` magic and declared size field in the real compiled `game.psp` both check out exactly against the actual file size.
- Not the graphics-mode gate in `FUN_0006f004` — it checks the display's reported color depth against 16/32-bit, but the query function `FUN_000d4a54` is hardcoded to always return `0x20`, so that check can never fail.
- Real, substantial GML source text is genuinely embedded and well-formed in the compiled `game.psp` (verified via `grep -a` for game-specific object names and GM8 syntax patterns like `with (`/`global.` — not generic placeholders, not the empty-code fallback).

An earlier pass concluded "not a GML compile error" from a live breakpoint on `FUN_000146a4` never firing across a full boot-to-exit run. **That breakpoint was on the wrong function** — established later in this same investigation (see the GMS1.4 section above): the actual error-reporter invoked by a *code action's* compile failure (`FUN_00000c30` → `FUN_00005284`) is `FUN_00014e3c`, a different function from the one a *script's* compile failure reports through. `FUN_000146a4` not firing proved nothing about code actions specifically.

**Actual root cause, found by extracting the runner's complete built-in GML function table (see "The runner's full GML support surface" above) and cross-referencing it against `Pillar of Autumn`'s own embedded GML** (isolated to the `STRG` chunk specifically — scanning the whole `game.psp` is far too noisy, since most of the file is unrelated compressed texture/audio binary data that incidentally matches an `identifier(` regex): the game's GML makes live, executed calls to **`d3d_light_define_ambient()`** (inside what's clearly a per-step ambient-light color cycler: `if counter==4{col=make_color_rgb(lum,lum,lum);d3d_light_define_ambient(col);counter=0;}`) and **`point_distance_3d()`** (feeding a light-priority queue: `ds_priority_add((global).light_queue,id,point_distance_3d(x,y,z,global.camx,...))`). Both are real, documented GM8.1 functions — and both are **confirmed absent** from this runner's function table (verified by direct string search of the decrypted ELF), even though sibling functions in the same families (`d3d_light_define_direction`, `d3d_light_define_point`, `point_distance`) are present. This runner's 3D/lighting API is an incomplete subset of GM8.1's own, and `Pillar of Autumn` implements a real-time 3D lighting system that happens to use exactly the missing pieces — triggering the same silent, no-error `PrepareGame` compile failure documented in the GMS1.4 section above, just via a different unsupported function than `draw_self()`.

Not independently re-confirmed with a fresh live breakpoint on `FUN_00014e3c` specifically for this game (the GMS1.4 test case already proved that mechanism conclusively, and re-running it here would be confirmatory, not new information) — but between the exact matching failure *shape*, the wrong-target explanation for the one piece of prior evidence that seemed to contradict this, and two independently-verified missing functions actually being called in live code, this is about as strong a conclusion as static analysis can produce without literally repeating the breakpoint. If it's ever worth fully closing the loop: breakpoint `FUN_00014e3c` (add `0x08804000` for the live address) against `Pillar of Autumn` specifically and read `a0` in PPSSPP's Memory view, exactly as done for the GMS1.4 case.

### RESOLVED (for the GMS1.4 loader's test project) — silent GML compile failure from an unsupported builtin function

The `FUN_000b24d4` breakpoint above was finally exercised for real against a controlled, minimal test case (the GMS1.4 `Sample.gmx` project, see below) and never fired — confirming the main loop genuinely never starts, for the same "exits silently, no crash, no error dialog" symptom as `Pillar of Autumn`. Tracing why, entirely via headless Ghidra decompilation plus a handful of live execute-breakpoints (address = Ghidra address + `0x08804000`), gave a full, concrete call chain:

`FUN_000cdb04` ("`RunnerLoadGame`/`PrepareGame` orchestrator") → `FUN_000c6304` ("PrepareGame", 8 sequential stages: data files, extensions, constants, scripts, timelines, **objects**, sounds, graphics — each stage logs `"Failed to ...''` via `FUN_000ce654` and aborts the whole game on any non-1 return, *before* `FUN_000b24d4` is ever reached) → for the object stage, `FUN_00083a00` (iterates all objects) → `FUN_00082910` (iterates one object's ~11 event slots) → `FUN_0001a96c` (iterates one event's actions) → `FUN_00000c30` (per action: for `Kind==ACT_CODE`/`ExeType==EXE_CODE`, copies the action's argument text into its `Code` field, then calls the real GML compiler `FUN_00005284`; on failure logs `"COMPILATION ERROR in code action\n%s"` via a shared logger `FUN_00014e3c` and returns 0, which propagates all the way back up to the "Failed to compile the actions in the objects." message and the silent abort).

**None of this produces any on-screen or otherwise user-visible error** — the runner's own debug-print calls don't reach PPSSPP's Log Console (they go through a function-pointer-based logger, `PTR_DAT_00149380+0x1c`, that isn't hooked to anything visible in this build) and the game simply calls `sceKernelExitGame()` and quits to a black screen a moment after boot.

For the test project specifically, the trigger was a single call to **`draw_self()`** added (as a debugging probe, to check whether the sprite/room/instance data was loading correctly) to an object's Draw event GML. Breaking on `FUN_00014e3c` and reading its `a0` argument out of PPSSPP's Memory view showed the actual compiler error text: `Error in code at line 1: ...at position 1` — i.e. a parse/resolve failure right at the very start of that statement. Removing the `draw_self()` call fixed the game completely: it now boots and runs normally end-to-end (remaining black screen at that point is an *expected* content gap — see the GMS1.4 section below — not a bug). This cut-down PSP build evidently doesn't implement every standard GM8 built-in function (the DND-only `action_*` functions are a previously-known example of the same kind of gap) — `draw_self()` appears to be another. Any not-yet-explained "boots then exits with no error" case (Pillar of Autumn included) should now be suspected of the same root cause first: an unsupported GML function or syntax construct causing a **silent** `PrepareGame` failure, not a data/format bug. The practical way to check is exactly the technique used here — breakpoint `FUN_00014e3c` (add `0x08804000` to get the live address), resume, and read the message text out of the `a0` pointer via PPSSPP's Memory view (right-click the register value → "Go to in Memory View" is far more reliable than typing the address by hand into the disassembly's own "Go to" field, which navigates code, not data).

Two new one-off Ghidra scripts were added to `ghidra_scripts/` for this investigation and are safe to reuse/repurpose: `FindWritesToAddr.java` (already existed; targets `DAT_001a7ab4`, the "running" flag) and `ReadStringAt.java` (reads and prints a null-terminated ASCII string at a given *static* address — useful for `.rodata` strings, not runtime-allocated buffers like the compiler error text above, which has to be read live instead). `DecompileNamed.java`'s hardcoded function-name list gets overwritten per investigation — check it before assuming it still targets what an earlier CLAUDE.md note says it does.

### The runner's full GML support surface — a static, ground-truth extraction

Rather than discover unsupported functions one Ghidra session at a time (as happened with `draw_self()` above), the runner's *entire* built-in GML function table was extracted in one pass: its `.rodata` holds several dense, contiguous runs of null-terminated identifier strings — one run per function category (data structures, movement/collision, math/string, sprites, sound, files, particles, D3D, etc.) — findable just by scanning for long unbroken sequences of short ASCII strings, no disassembly needed. This recovered **1220 confirmed real, supported GML functions** plus the full sets of built-in constants (colors, keys, event codes, blend modes...) and built-in instance variables (`x`, `y`, `hspeed`, `room_speed`, ...). The full function list lives in [`GMAssetCompiler/RunnerSupportedFunctions.cs`](GMAssetCompiler/RunnerSupportedFunctions.cs) (a plain `HashSet<string>`, intended for a future compile-time validator — see "best practice for complete 1.4 support" below); re-run the same scan against a fresh decrypt if the runner binary ever changes.

(The initial extraction pass came back with 1240 candidate names; 20 were removed after review as not genuinely supported by this runner — `show_image`, `show_info`, `show_text`, `show_video`, and all 16 `splash_*` functions. Worth remembering if the scan is ever re-run: contiguous-ASCII-run scanning finds *candidate* identifiers appearing somewhere in `.rodata`, not confirmed registered native functions — a name can be real GM8.1 API and still not be one this specific cut-down PSP port actually implements, or can be scan noise entirely unrelated to the function table. Cross-check anything before trusting it as truly supported.)

**The result versus GameMaker: Studio 1.4 is one-sided, not a mix of gaps.** Checking a representative sample of every major feature area GameMaker gained *after* GM8.1 — buffers, Box2D physics, shaders, GPU state functions (`gpu_set_*`), modern gamepad input (`gamepad_*`, as opposed to the legacy `joystick_*` this runner does have), extended networking beyond the legacy DirectPlay-style `mplay_*`, JSON/base64/MD5/SHA1, OS/mobile/cross-platform functions (`os_*`, `device_*`), Steam/achievement integration, and even small GML-level conveniences added post-GM8.1 like `draw_self()`, `instance_create_depth()`, `clamp()`, `lerp()`, and `dot_product()` — **none of it exists in this runner at all**: every single function checked across every one of those categories came back absent. This runner is not "GM8.1 plus a few gaps" relative to GMS1.4 — it is exactly the GM8.0/8.1-era function surface (confirmed: exactly what `RunnerSupportedFunctions.cs` contains) and nothing added since. Anything a GMS1.4 project's GML calls that isn't in that file should be assumed unsupported until proven otherwise, full stop — there's no need to re-litigate this per-function going forward.

### Best practice for complete GMS1.4 support going forward

Given the above, "supporting GMS1.4" for this target splits into two very different kinds of work, worth keeping separate:

1. **Loader/XML completeness (low-risk, proven pattern) — done, except extensions.** Sounds, backgrounds, paths, fonts, timelines, and room tiles are all implemented now (see the GM8.1-vs-GMS1.4 differences list below for each). Extensions remain the one unimplemented `.gmx` resource type, since no test project has exercised them yet and the mapping wasn't worked out.
2. **Catching unsupported-GML failures before they become silent on-device crashes — done, for both targets.** `GMLFunctionValidator` (`GMAssetCompiler/GMLFunctionValidator.cs`) scans every script and code-action's GML for `identifier(` call sites, skips GML keywords/operators (`if`/`while`/`with`/`repeat`/`div`/`mod`/...) and the project's own script names, and warns on anything left that isn't in `RunnerSupportedFunctions.Names`. Wired into both `Loader.LoadGMS14Project` and `Loader.LoadGMK` (the GM8.1 `.exe` path) right before each returns, so it runs automatically on every compile regardless of target. Verified against the exact `draw_self()` case that originally required a full Ghidra + live-PPSSPP-breakpoint session to diagnose: reintroducing that one call now produces an immediate `Warning: 'obj_player' calls 'draw_self', which is not in this runner's supported GML function table...` at compile time, on the PC, with the project's actually-clean state producing no warnings at all. Also re-ran against the real `Pillar of Autumn V1.exe` (GM8.1 target) and it correctly flagged both `d3d_light_define_ambient` and `point_distance_3d` — the exact two functions root-caused for that game's mystery earlier in this file — confirming the validator actually catches real-world cases, not just the synthetic test project.
   - **Known source of noise, not a bug in the validator**: extensions aren't parsed by this loader at all yet (see "Not yet implemented" above), so any GML calling into a genuine third-party extension's functions will be flagged as "unsupported" even though it's perfectly valid — `Pillar of Autumn` does exactly this with ~103 calls into what's almost certainly a bundled `SS_*` sound-effects extension (`SS_PlaySound`, `SS_LoadSound`, `SS_StopSound`, `SS_LoopSound`, `SS_SetSoundVol`, `SS_Init`). A handful of other single-occurrence hits (`mouse_wheel_up`, `copyright`, `save`, `zx`) are low-confidence and likely just coincidental regex matches inside this particular game's heavily obfuscated identifier names, not real calls. Treat multiple/repeated hits on a plausible extension-style name pattern as probably-fine noise; treat a real, recognizable GM8.1 manual function name (like the two `d3d_`/`point_` ones) as the signal worth acting on.

**The validator's warnings (and every other `Console.WriteLine` in this tool) are invisible in the plain GUI flow, so a console window is now opened for it.** WinForms apps (`OutputType=WinExe`) have no console attached when launched normally (double-click), so `Console.WriteLine` output was previously discarded silently for GUI users — the CLI/`--headless` path only ever showed it because that's normally run from an existing terminal. `Program.Main` now calls `AllocConsole()` (P/Invoke, `kernel32.dll`) right before showing the `ChovyUI` dialog, titled "CHOVY-GM Build Log" — a real, separate Win32 console window that stays open alongside the GUI and shows every warning/progress message live. `--headless` mode is unaffected (it already inherits its parent shell's console; `AllocConsole` is a documented no-op when a console is already attached — though note that if you test this by launching the GUI build with its own stdout *already* redirected to a file, e.g. `foo.exe > log.txt`, .NET's `Console.Out` can end up still bound to that original redirected handle rather than the newly-allocated console, since `AllocConsole` operates at the Win32 level and doesn't automatically rebind an already-cached .NET `TextWriter` — a real double-click launch, or `Start-Process` with no redirection, doesn't have this wrinkle).

Runner *binary* patching (adding genuinely new engine functionality — a second GUI-space rendering pass, physics, etc.) is a separate, much larger, higher-risk category of work — full new engine features, not fixes — and should only be scoped per-feature if a real project actually needs one specifically enough to justify it.

A secondary, likely-inconsequential finding along the way: `neonquest.exe` (works) embeds an internal asset-format version of `700`/`701`, producing an IFF chunk tag of `GEN7`; `Pillar of Autumn` (was already broken) embeds `810`, producing `GEN8` — `IFFSaver.WriteHeader` picks the tag name off `_assets.Version` but writes an *identical* header body either way (verified: `.Version` is read in exactly one place in all of `IFFSaver.cs`). Switching the GMS1.4 loader's synthesized `GMAssets.Version` from `810` to `700` (to match the one confirmed-working real game) did **not**, on its own, fix the exit-without-error bug — the `draw_self()` compile failure above did. Whether `GEN7` vs `GEN8` matters at all to the runner is therefore still unconfirmed either way; `700` was kept in `GMAssets`'s plain constructor regardless, since it's the only value with a real working precedent.

**After fixing the crash, a second, unrelated bug remained: nothing rendered.** With `draw_self()` removed the game booted and ran indefinitely (no exit) but showed a plain black screen — expected in itself (black room background, and no font support yet means `draw_text()` has nothing to render with), but a follow-up `draw_sprite(spr_player, 0, x, y)` call *also* produced nothing, with no crash either. The actual cause turned out to be the Draw-GUI `enumb` issue described above in the differences list: the object's Draw event was being stored under sub-event `64`, which this runner's Draw dispatch never looks at, so the whole event body (both the sprite draw and the text draws) silently never executed at all — it wasn't a rendering-pipeline bug. Forcing event-type-8 sub-events to `0` in `Loader.LoadGMS14Object` fixed it immediately; the sprite and text both render correctly. This is the same "silent, no error, looks like a rendering bug but isn't" failure shape as the `PrepareGame` issue above, just one layer further into actual execution — worth remembering as a general debugging instinct for this codebase.

## GameMaker: Studio 1.4 target — GM8.1 vs. GMS1.4 differences

A second compile target was added (`--target-gms14` conceptually; selected via `--headless ... gms14` on the CLI, or the new Target radio buttons in `ChovyUI`) that loads a GameMaker: Studio 1.4 `.gmx` project instead of a GM8.1 standalone `.exe`. Both targets ultimately build the same in-memory `GMAssets` graph that the rest of the compiler (GML compilation, texture packing, `IFFSaver`) already consumes, but getting there is different enough to be worth its own notes. Implementation lives in `Loader.LoadGMS14Project` (`GMAssetCompiler/Loader.cs`), exercised against a real minimal project at `Sample.gmx` (VM export, not YYC).

**Confirmed working end-to-end, including on-device rendering** — not just "compiles": `Sample.gmx` (a sprite, a font, a sound, two backgrounds, a path, a timeline, an object with Create/Step/Draw events and a script call, a room with one instance and three tiles) compiles via `--headless ... gms14` into a valid `game.psp`, boots through the decrypted `KAROSHI.BIN` runner in PPSSPP without the runner exiting early, and `draw_sprite()`/`draw_text()`/`draw_set_font()` all render correctly on screen, with the room's tiles visibly rendered too — full alphabet, digits, and case all verified character-by-character. Getting from "compiles" to "actually renders correctly" surfaced three more real bugs on top of the format differences below: two silent `PrepareGame` failures (see "Silent GML compile failure" and the Draw-GUI point) and one genuinely wrong-but-not-crashing font glyph mapping (see the font bullet below) — none of which were compile errors, so each needed actual on-screen verification to catch, not just "it built successfully." Sounds/paths/timelines are loaded and compile cleanly (audio converts to AT3) but aren't separately exercised by anything visible in the test scene beyond compiling without error.

- **No embedded/encrypted executable at all.** A GM8.1 target is a self-contained `.exe` with the asset data XOR/CRC-encrypted and buried inside it (`Loader.CheckFor8_1`/`Process_Encrypt`); a `.gmx` project is a plain, uncompressed directory tree of XML files with no encryption or compression step whatsoever. There is nothing to decrypt or search for — the master `<name>.project.gmx` file is read directly and just lists relative paths to every other resource file.
- **Resources are named, not indexed, in the source data.** GM8.1's binary format stores resources as a flat, order-dependent list where cross-references (an object's sprite, an instance's object, a view's followed object) are plain integer indices into that list. GMS1.4's XML instead references everything **by string name** (`<spriteName>spr_player</spriteName>`, `objName="obj_player"`, etc.) and uses the literal string `<undefined>` (not a numeric sentinel) where GM8.1 would use `-1`. The loader has to build name→index maps as it loads each resource category, and does a two-pass load of objects specifically so a `parentName`/mask reference to an object elsewhere in the same list still resolves.
- **Sprites reference loose PNG frame files**, not embedded bitmap streams. Each `<sprite>` XML lists `<frames><frame index="N">images\name_N.png</frame></frames>` paths relative to the sprite's own folder; `GMBitmap32.FromFile` loads each with `System.Drawing.Bitmap` and repacks it into the same per-pixel BGRA byte layout the GM8.1 stream-reading constructor produces, so the rest of the pipeline (texture packing, `CreateMask`) needs no changes.
- **Scripts are loose plain-text `.gml` files**, not a versioned/encrypted binary blob (`GMScript`'s GM8.1 constructor branches on a version tag and, for older versions, XOR-decrypts the script text with a fixed key `12345`). A `.gmx` script resource is literally just the GML source, `File.ReadAllText`'d directly.
- **Object events name their type/subtype via XML attributes, not an implicit binary array position.** GM8.1 stores an object's events as up to 12 fixed positional "slots" (event type 0–11: Create, Destroy, Alarm, Step, Collision, Keyboard, Mouse, Other, Draw, KeyPress, KeyRelease, Trigger), each holding a sparse list of `(subevent, event)` pairs read until a sentinel. GMS1.4's XML instead has one flat `<events><event eventtype="N" enumb="M">` list; the loader still has to bucket these back into the same 12-slot shape, because `IFFSaver.WriteObjects` (and, presumably, the on-device reader) expect that shape unchanged.
- **GMS1.4's IDE now defaults a newly-added Draw event to "Draw GUI" (`enumb="64"`), not classic Draw (`enumb="0"`).** This PSP runner is a GM8.1-era engine whose per-frame Draw dispatch only ever looks for subevent `0` — it has no concept of GMS's newer Draw sub-events (`64`=GUI, `65`=Resize, `72`/`73`=Begin/End, `76`/`77`=Pre/Post), all added to GameMaker well after this runner was built. A Draw event exported straight through with `enumb=64` silently never runs (no crash, no error — the render code is just never called), so `Loader.LoadGMS14Object` forces every event-type-8 (Draw) sub-event down to `0` unconditionally. This means GMS1.4's Draw GUI/Begin/End/Pre/Post distinctions are all collapsed into one classic Draw call for this target — there is no way to preserve them separately on this runner.
- **Not every action in a `.gmx` event is a plain GML code action, and mixing them up fails silently, not loudly.** A GML code block dropped into an event exports as `<kind>7</kind>`/`<exetype>2</exetype>` (matching `eAction.ACT_CODE`/`eExecuteTypes.EXE_CODE`) with its actual source text sitting in `<arguments><argument><string>` rather than the otherwise-present-but-empty `<codestring>` element — this lines up exactly with `GMAction`'s existing `GMAction(int _id, string _code)` convenience constructor (already used elsewhere for DND-removal). But a genuine drag-and-drop library action (`<kind>0</kind>`, a `<functionname>` like `action_move`/`action_kill_object`, and one or more separately-typed `<arguments>` instead of a single GML string — confirmed via a real GMS1.4-authored timeline using exactly this shape) has no GML source to extract at all. Blindly wrapping its first argument as if it *were* GML code doesn't error — depending on the argument text, it either fails to compile (loud, safe) or **compiles successfully into a meaningless no-op expression statement** (silent, wrong: the action is "there" but does nothing). `Loader.LoadGMS14Action` now checks `<kind>` first and returns `null` (skipped, with a clear console warning naming the dropped action) for anything that isn't `ACT_CODE`, rather than risk the silent case — drag-and-drop actions remain genuinely out of scope, but the failure mode is now "clearly missing" instead of "silently wrong."
- **Numeric formatting differs where GM8.1 used raw binary integers/doubles.** Room instance `colour` is a `uint` written as its full decimal text form in XML (e.g. `colour="4294967295"` for `0xFFFFFFFF`/no tint) rather than a 32-bit binary field; `scaleX`/`scaleY`/`rotation` are plain culture-invariant decimal text. Boolean-ish XML elements/attributes generally follow classic GM convention (`-1` = true, `0` = false) rather than a single encoded bit.
- **Instance IDs aren't present in the XML at all.** GM8.1's binary format assigns each room instance a persistent integer `Id` used internally; a `.gmx` `<instance>` only has a GUID-like string `name` attribute (e.g. `inst_D5BCBF01`) meant for the IDE, not the runtime. The loader synthesizes its own sequential integer ids (starting at 100000) since nothing downstream appears to depend on their exact value, only their uniqueness.
- **Fonts export a pre-rendered glyph atlas PNG, so there's no rasterization to reimplement** — unlike GM8.1's own binary format, where the glyph bitmap is rendered and embedded by the IDE at compile time, a `.gmx` font resource ships its already-rendered atlas image (`<image>name.png</image>`, white glyphs on transparent, same convention `IFFSaver` already expects) plus per-glyph pixel metrics (`<glyph character="65" x="…" y="…" w="…" h="…" shift="…" offset="…"/>`) directly in the XML. Loading one is exactly as simple as loading a sprite frame.
- **Font glyphs are looked up by raw character code, not by an offset from `First`, and GM8.1's binary format always has exactly 256 glyph slots because of it.** `GMFont`'s GM8.1 Stream constructor unconditionally reads 256 glyph entries regardless of the font's actual range — `First`/`Last` are just metadata, not a basis for indexing. A `.gmx` font's XML only lists the glyphs that actually exist (e.g. character codes 32–127), so `Loader.LoadGMS14Font` has to place each one at its real character-code index in a full 256-slot array (with everything else a blank/all-zero placeholder glyph), not just append the ~96 real glyphs as a shorter list. Getting this wrong doesn't crash or error at all — it silently renders the *wrong but real-looking* glyph for every character (empirically: every letter rendered as the letter 32 codepoints away — `A`→`a`, `N`→`n` — and digits rendered as blank, consistent with the runner effectively computing `list[code]` against a too-short, wrongly-based list). This is the kind of bug that only on-screen verification catches; the compiler and runner both accept the malformed data without complaint.
- **Sounds reference a loose audio file plus metadata, mirroring the sprite pattern.** A `.gmx` sound resource (`<sound>...<data>name.wav</data></sound>`) points at its actual audio file in a sibling `audio\` folder (`<origname>sound\audio\name.wav</origname>` confirms the layout) rather than embedding compressed audio data with a version-tagged header the way GM8.1's binary format does; `Loader.LoadGMS14Sound` just reads the raw bytes with `File.ReadAllBytes` and lets the existing AT3-conversion step in `IFFSaver`/`Program` handle the rest unchanged, the same as it already does for GM8.1-sourced `.wav` sounds.
- **A background's "is this a tileset" flag is an explicit, directly-authored property (`<istileset>-1</istileset>`), not something derived from how rooms use it.** GM8.1's own `GMBackground.Tileset` is `false` by construction in its binary-reading path and only gets set `true` after the fact by `Loader.TagBackgroundTilesets` scanning which backgrounds any room's tiles actually reference. GMS1.4 exposes the same concept as a first-class editable resource property instead, so `Loader.LoadGMS14Background` reads `istileset` directly — arguably more accurate than the derived approach, though also currently moot: this loader doesn't parse room `<tiles>` yet (see below), so nothing consumes the flag either way yet.
- **Paths are a flat, self-contained point list** — `<points><point>x,y,speed</point>...</points>`, one comma-separated triple per line, with `kind`/`closed`/`precision` as simple sibling elements. No cross-resource references at all, the most straightforward resource type implemented so far.
- **Room tiles reference their source background by name and a source-rectangle offset, with their own explicit id** — `<tile bgName="background0" x="96" y="64" w="16" h="16" xo="96" yo="48" id="10000004" .../>`, where `x`/`y` is the tile's position in the room and `xo`/`yo` is where to crop from inside the named background's image (matching `GMTile`'s existing `X,Y` vs `XO,YO` field split exactly). Unlike room instances, tiles already carry a real, stable `id` in the XML — no need to synthesize one. The room's own `<backgrounds>` *layer* entries (the 8 fixed background-layer slots, separate from tile placement) also reference a background by `name` the same way; both resolve through the same background name→index map built while loading `<backgrounds>` at the project level.
- **A background's "is this a tileset" flag is redundant but still worth trusting twice.** `Loader.LoadGMS14Background` already reads `istileset` directly (see above), but `Loader.TagBackgroundTilesets` — the existing GM8.1-path helper that derives the same flag from which backgrounds a room's tiles actually reference — is called for the GMS1.4 path too now that tiles are implemented, as a cheap safety net in case a background is used as a tile source without being explicitly marked.
- **Not yet implemented for this target**, because the test project didn't exercise it and the mapping from `.gmx` XML to `GMAssets` wasn't worked out: extensions.
